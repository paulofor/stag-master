# Matriz de homologação da versão 0.4.10

Definida antes da implementação dos testes. O aplicativo é desktop Windows; Chromium em dimensões compactas e emulação Pixel 7 validam layout, toque e acessibilidade, sem implicar suporte a app Android. A sandbox Linux não possui sessão gráfica Windows, OAuth interativo do cliente nem ferramentas nativas Windows. Essas limitações são registradas separadamente dos testes locais.

## Fontes de documentação por projeto — versão 0.4.10

Matriz definida antes dos testes. O STAG não tinha cadastro de URLs por projeto nem regressões para atualizar as fontes de uma conversa em andamento. A interface passa a oferecer **Fontes do projeto**, com nome e URL, edição, remoção e salvamento local por pasta. O cadastro é contexto de referência para o modelo; não concede autorização ao navegador nem torna páginas ou nomes de fontes instruções superiores. A consulta usa somente `stag_browser`, preservando a fila e as políticas existentes.

| Validação                  | HTTP(S), sem credenciais na URL; nomes/URLs limitados, até 20 fontes, duplicatas normalizadas e campos extras recusados; erros não exibem dados da URL                                           | Schemas de produção + IPC + interface                 |
| Integração do agente       | Start/resume recebem lista vigente; salvar numa conversa atual atualiza o contrato antes do próximo turno; remoção não mantém fontes antigas no contrato; consulta pertinente e após compactação | RPC determinístico + provedor loopback com Codex real |

O harness deve demonstrar a entrega do contrato ao provedor e a recuperação, sem afirmar obediência semântica absoluta do modelo. A sandbox Linux não comprova execução nativa Windows nem acesso a documentação privada do cliente. Este produto desktop entrega instalador como artefato; não há deploy web.

A rodada focalizada revelou duas diferenças: Tab podia sair para a barra do Chromium, e resume de thread já carregado não transmitia a nova lista ao provedor real. O dialog agora limita a circulação do foco. O serviço envia a lista vigente como `additionalContext` de tipo `untrusted` em cada turno, acompanhada da política fixa e capacidade atual como `application`. O smoke verifica o campo/kinds no schema real e a presença das fontes iniciais/atualizadas no provedor loopback, evitando tratar apenas um request aceito como prova de entrega ao modelo. O corpus testa perda desse contexto e recuperação. Nenhuma credencial real ou inferência paga é utilizada.

Na revisão do envio, a retomada assíncrona ainda ocorria antes de adquirir o bloqueio de envio, permitindo dois pedidos simultâneos nesse intervalo. O bloqueio agora cobre a retomada e é liberado também quando ela falha. Uma regressão com retomada controlada verifica segundo envio/cadastro recusados, um único turno novo e recuperação; o fluxo completo do serviço e Electron é revalidado após esse ajuste.

Evidência local: `npm run check` passou com 255 contratos, typecheck/build, Codex real com fontes atualizadas no provedor sintético e 46 cenários Chromium (amplo, compacto e Pixel 7). Após a correção de serialização identificada na revisão, os 115 testes de serviço/fontes passaram (256 contratos no total), assim como typecheck, build e `xvfb-run -a npm run test:desktop` atualizado, incluindo consulta pelo navegador de produção, preservação da sessão ao abrir o cadastro e reinício real com fontes salvas. Screenshots do cadastro foram inspecionados. Sintaxe dos scripts JavaScript, `format:check` e revisão do diff são conferidos antes da entrega. Não há scripts shell alterados. O kernel Linux bloqueia namespaces bwrap; o smoke não apresenta essa falha de inicialização como prova de bloqueio de arquivos. Execução nativa Windows, políticas do sandbox e instalador 0.4.10 dependem dos jobs Windows do PR/main; acesso a documentação privada e interpretação do LLM não são homologados por fixtures.

O primeiro job Windows do PR aprovou contratos, driver nativo, instalador e smoke, mas falhou no reset do navegador: limites aceitos anteriormente já não cabiam na área útil da janela. A redução de janela foi forçada no harness local e reproduziu o mesmo erro antes da correção. Reset e mudança de visibilidade agora descartam somente o layout interno obsoleto, mantendo a view oculta até receber novos bounds válidos; bounds externos continuam recusados quando ultrapassam a janela. O harness verifica redução real, sessão descartada/recuperada, visibilidade, restauração do tamanho e preservação da recusa explícita de bounds inválidos. Build/typecheck, navegador Electron e regressões de browser/serviço são repetidos localmente antes de atualizar o mesmo PR.

## Preparação Git ao selecionar a pasta — versão 0.4.9

Matriz definida antes dos testes. A seleção de pasta não procurava repositórios nem tratava `dubious ownership`; o harness usava pastas sem `.git`. O STAG passa a percorrer a pasta e suas subpastas, cadastrar raízes exatas em `safe.directory` global e verificar `status --short --branch`. A seleção autoriza essa preparação local, sem senha, rede ou elevação. Não se cadastra `*`, não se seguem links/junctions nem metadados Git para fora da pasta. O relatório distingue cadastro, verificação e falhas; a conversa continua disponível quando o Git falha.

O cadastro resolve confiança de propriedade do Git; não concede permissões NTFS/GPO, autenticação remota, desktop ou navegador. Falhas não são apresentadas como sucesso. A consulta automática desativa callbacks e escrita opcional do índice. As proteções são verificadas pelo código e Git real, sem depender de uma resposta predefinida do modelo. Linux não comprova a execução nativa Windows.

Evidência local: `npm run check` executou typecheck, 244 contratos, build, smoke real isolado e 40 cenários de interface. Dois cenários de imagens revelaram um seletor ambíguo após a adição do segundo aviso de status; os avisos receberam nomes acessíveis e ambos passaram na repetição focalizada. O harness Electron também passou após aguardar o término da segunda seleção, em vez de ler seu progresso como resultado final. A revisão reproduziu que `--git-dir` explícito ignora a verificação de propriedade do Git; a consulta usa descoberta normal com `-C` e uma nova regressão verifica confiança retirada durante a preparação. Os 13 testes Git passaram (245 contratos no total), assim como typecheck/build/smoke atualizados, `xvfb-run -a npm run test:desktop`, sintaxe JavaScript, `format:check` e inspeção visual compacta/Pixel 7. Nenhum dado ou configuração Git real do usuário foi usado. A sandbox Linux bloqueia namespaces bwrap; a prova de confiança no executor nativo Codex, políticas Windows e instalador 0.4.9 deve passar nos jobs Windows do PR/main.

A primeira execução do PR aprovou os contratos/UI Linux e os contratos, driver e empacotamento Windows. O probe Git dentro do sandbox falhou ao iniciar o subprocesso; sua mensagem genérica ocultou o código do erro. O harness passou a resolver o binário Git antes da entrada no sandbox, como já faz com o Node, e a registrar somente o código de inicialização e a classificação de propriedade, sem stdout/stderr ou ambiente. Uma regressão local reproduziu a falha de resolução com PATH restrito e comprovou o funcionamento com o executável absoluto; também distingue `dubious ownership` de executável ausente. Typecheck, 16 testes focados, smoke e Electron foram revalidados antes de atualizar o mesmo PR. A causa específica do primeiro processo Windows não é afirmada sem seu código original; o job atualizado deve comprovar o fluxo nativo completo. A suíte passa a conter 246 contratos.

O segundo job Windows identificou `EPERM` na criação do subprocesso Git aninhado dentro do Node do probe, inclusive com caminho absoluto. Esse lançamento extra foi removido: o smoke pede ao próprio `command/exec` para executar o Git, mantendo a política de produção e passando apenas a variável sintética de propriedade via `env`, presente no schema real. A regressão local do adaptador exercita Git real com PATH restrito, falta de confiança, sucesso após cadastro, `EPERM` recusado e o erro RPC específico de propriedade do vizinho. Typecheck, os 16 testes focados, smoke e Electron passaram antes da nova atualização. Nenhuma ACL, política Windows, modo de sandbox ou código de produção foi afrouxado.

## DBeaver no desktop permitido — versão 0.4.8

Matriz definida antes dos testes desta alteração. A lista de produção ainda recusava DBeaver, enquanto o harness verificava produto/assinatura inválidos somente no VS Code. DBeaver passa a integrar a lista com Postman, IntelliJ IDEA e Visual Studio Code, sob o mesmo consentimento por conversa, validação de identidade, captura por janela e fila compartilhada. O executável oficial `dbeaver.exe` do [DBeaver Community 26.2.2](https://github.com/dbeaver/dbeaver/releases/tag/26.2.2) foi inspecionado sem execução: produto `DBeaver Community` e certificado com nome `DBeaver Corp`. O driver aceita produto `DBeaver` ou `DBeaver Community` e exige assinatura válida desse fornecedor; não aceita nomes semelhantes, outros produtos ou executáveis sem assinatura. A inspeção do certificado no Linux não comprova a confiança Authenticode no Windows.

O teste `test:desktop` abre uma janela Electron real e valida protocolo local, preload isolado, origem IPC e seleção de projeto. No Linux (Xvfb), também exercita login, conversa e aprovação por um processo simulado; no Windows usa o Codex real isolado, sem OAuth.

## Execução do controle sob política PowerShell restritiva

Matriz definida antes dos testes desta correção. A política é definida somente no processo filho que executa o script empacotado, após aprovação da operação. Os testes não alteram políticas persistentes nem usam as janelas do cliente.

Políticas de grupo continuam tendo precedência e não são contornadas.

## Confirmação nos pontos críticos

Matriz definida antes dos testes da nova política. A autorização inicial vale somente para a conversa em memória. O agente deve declarar o risco e a intenção de cliques, texto e atalhos; coordenadas sozinhas não determinam a consequência. Exclusão, envio externo, publicação, pagamento, uso de credenciais e alterações no sistema são críticos. Sem contexto suficiente, o serviço pede confirmação. Enter, Delete, atalhos desconhecidos e texto com quebras de linha/tabulação também exigem confirmação por poderem enviar, executar ou mudar o alvo. Capturas, foco, rolagem e navegação/edição local identificadas como rotineiras usam a autorização inicial.

| Área                    | Cenário e aceite                                                                                                                                                                         | Evidência prevista                  |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| Caminho feliz           | Sequência de leitura, captura, foco, clique, texto local, atalho seguro e rolagem termina sem cards intermediários; resultado autoritativo permanece visível                             | Serviço bidirecional + E2E Chromium |
| Pontos críticos         | Cada efeito crítico aguarda confirmação com intenção, alvo e parâmetros; recusa não executa; nova tentativa exige nova confirmação                                                       | Classificador + serviço + E2E       |
| Validações              | Contexto ausente pede confirmação; risco inválido/campos extras não executam; Enter/Delete, sequência de atalhos e texto que envia Enter não são liberados por declaração routine        | Unidade do contrato e serviço       |
| Integração              | Schema de produção aceito pelo Codex fixado; instruções de start/resume descrevem rotina, criticidade e proibição de contornar recusa                                                    | Smoke real isolado + serviço        |
| Recuperação             | Falhas respondem ao agente e contam nas métricas; ações são serializadas; pedidos repetidos não executam duas vezes; interrupção impede ações enfileiradas e descarta resultados antigos | Fixture determinística + serviço    |
| Isolamento              | Nova conversa, revogação e outro thread não herdam consentimento; reconectar o mesmo thread mantém acesso; histórico antigo sem contexto conserva confirmações de interação              | Serviço + E2E                       |
| Observabilidade e dados | Status de execução/conclusão e contadores locais preservados, sem pixels ou payloads de autenticação no renderer; apenas janelas/imagens/projetos sintéticos                             | Serviço + fixtures                  |
| Interface e plataforma  | Painel único em 640×900, 1280×800 e Pixel 7; confirmação inicial explica autonomia e dados enviados; Linux sem controle nativo                                                           | E2E + Electron real em Xvfb         |
| Windows e entrega       | Driver e políticas preservados; job Windows executa testes nativos e gera instalador sem publicar release; interação real continua exigindo sessão do cliente                            | test:windows + dist:win no CI       |

A lacuna concreta do harness era a ausência de contexto sobre o efeito das interações e de regressões para execução automática. O contrato, as instruções e as fixtures agora devem distinguir rotina de criticidade e cobrir serialização, duplicidade e cancelamento. A classificação semântica de cliques depende da interpretação da tela pelo agente; não há inspeção semântica nativa dos controles de todos os aplicativos.

O primeiro job Windows desta alteração expirou sem saída ao iniciar a fixture nativa com compilação C# sob prazo de 15 s. O harness dá agora 60 s aos processos de validação/diagnóstico e registra o início de cada etapa, a compilação sintética e a execução do dispatcher. O driver de produção mantém seu prazo de 15 s, também exercitado pelo teste Restricted; esse prazo não foi ampliado. A regressão nativa é conferida novamente no job Windows do mesmo PR, pois a sandbox local é Linux.

O OAuth real requer ação do cliente no navegador da sua máquina. A interação nativa com aplicativos Windows requer homologação manual em sessão Windows interativa; não é declarada como testada em Linux. Não há backend hospedado ou deploy web: a entrega desktop gera um instalador como artefato do workflow, sem certificado de assinatura nesta versão.

## Navegador ao lado da conversa — versão 0.4.0

Matriz definida antes dos testes do novo fluxo. O conteúdo remoto usa uma WebContentsView isolada, sem preload/Node; o App Server recebe uma ferramenta de operações fixas. A autorização do navegador vale apenas para a conversa em memória. Todos os sites, credenciais de formulário, imagens e dados desta homologação são sintéticos, servidos em loopback; não são usados serviços reais ou sessões do cliente.

| Área                     | Cenário e aceite                                                                                                                                                                                  | Evidência prevista                                      |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| Caminho feliz            | Conversa à esquerda e navegador à direita; endereço, voltar/avançar/recarregar; modelo navega, lê elementos, preenche, seleciona, clica, rola e captura                                           | Electron real com site sintético + serviço bidirecional |
| Autorização              | Permitir uma vez na conversa; rotina sem cards; revogar/fechar/nova conversa descartam acesso e sessão; histórico antigo não ganha ferramenta nem política nova                                   | Serviço + Electron + E2E                                |

| Validações               | Somente HTTP(S); campos extras, JavaScript arbitrário, refs/página antigos, campos desabilitados, upload e alvo alterado recusados                                                                | Unidade + Electron                                      |

| Observabilidade          | URL/título/carga/erro/estado de controle visíveis; tool autoritativo no chat; contadores locais de falhas; snapshots públicos sem pixels, valores de campos ou cookies                            | Serviço + E2E + Electron                                |
| Segregação               | Partição efêmera por conversa, sem cookies do navegador do cliente; projeto e CODEX_HOME temporários; troca de conversa destrói conteúdo remoto anterior                                          | Electron + serviço                                      |

| Windows e entrega        | Testes nativos preservados; navegador real e instalador executados no job Windows; artefato 0.4.0 sem publicação de release                                                                       | test:windows, test:desktop e dist:win no CI             |

Lacuna observada do harness: somente o desktop era simulado; não havia site sintético nem regressão para efeitos DOM ou conteúdo remoto dentro do aplicativo. O novo fluxo deve compartilhar a fila existente e acrescentar testes Electron com o driver de navegador de produção, referências de elementos e isolamento real. Linux comprova Chromium/Electron e contratos; OAuth real, sites com restrições de navegador embutido e interação com aplicativos Windows do cliente continuam exigindo homologação na sessão do cliente.

Evidência local desta implementação: `npm run check` aprovado (contratos, build, handshake real e 24 cenários de interface); a regressão final de revogação foi confirmada pelos 56 testes do serviço. `xvfb-run -a npm run test:desktop` aprovado com navegador de produção: preenchimento pelo App Server simulado sem cards, envio recusado sem efeito, envio permitido uma vez, senha confirmada, autorização cancelada/expirada, alvos antigos recusados, sessão descartada, WebSocket sintético, bloqueio de popups/downloads e recuperação de carga interrompida. A revisão identificou e corrigiu a revogação antes do pedido de interrupção remoto, preservando a recusa mesmo quando esse pedido falha. O harness usa a descoberta do Electron fixado pelo Playwright, que carrega seu inicializador; informar executablePath explicitamente impedia esse inicializador na versão instalada. Erros de operações DOM são devolvidos com mensagem legível pelo script fixo em mundo isolado. `format:check` e verificação sintática dos scripts JavaScript aprovados. A regressão de troca de sessão durante o foco confirma que nenhuma tecla pendente é enviada ao novo navegador. O job Windows precisa confirmar os contratos nativos e o instalador do HEAD antes do merge.

O primeiro job Windows do navegador aprovou contratos, driver Restricted, empacotamento e handshake, mas o harness Electron usou dimensões fixas maiores que a área útil da janela do runner. A regressão usa agora uma janela compacta, aguarda o carregamento antes de medir a área útil com `getContentSize()` e confirma a recusa de limites externos; a validação de produção permanece preservada. O fluxo do navegador é repetido localmente e no mesmo PR antes do merge.
